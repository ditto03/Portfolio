SIEM Log Analysis & Threat Detection using Splunk

Standing up Splunk as a lightweight SIEM to monitor a Linux server's SSH authentication log in real time, and building a detection rule that catches unauthorized login attempts as they happen.

CategorySOC / SIEM Monitoring
EnvironmentKali Linux → Ubuntu Server (SSH)
PlatformSplunk Enterprise
TypeCybersecurity Training Project

Objective

Failed SSH logins are one of the first signals a SOC analyst learns to watch — they can mean a user mistyped a password, or they can be the leading edge of a brute-force attempt. The goal of this project was to build the monitoring pipeline that turns that raw log noise into a real-time, actionable alert: ingest a Linux server's authentication log into Splunk, search it for failed password events, and configure an alert that fires the moment one occurs.

Environment

The setup used two machines: a Kali Linux box acting as the connecting client, and an Ubuntu server as the monitored host running Splunk Enterprise. Connectivity between the two was established over SSH before any log configuration began.

Note from the field

An early wrong password during the initial SSH connection wasn't a problem — that failed attempt is exactly the kind of event the detection rule is designed to catch later, so it made a useful first test case.

Building the detection pipeline

  1. Connect over SSH — established the Kali-to-Ubuntu SSH session that would generate the authentication events to monitor.
  2. Log into Splunk — accessed the Splunk Enterprise web console on the Ubuntu host.
  3. Add the data source — under Settings → Add Data → Monitor, pointed Splunk at /var/log/auth.log to continuously monitor the file.
  4. Set the source type — classified the input as linux_secure so Splunk parses the authentication events correctly.
  5. Review and submit — confirmed the input settings (host value, index, continuous monitoring) and submitted the configuration.
  6. Search the ingested data — ran a search to confirm events were flowing in, then filtered specifically for failed password attempts.

The search query

Once the log source was live, the following search isolated failed SSH login attempts from the full authentication event stream:

# Confirm ingestion source="/var/log/auth.log" host="ubuntu" sourcetype="linux_secure" # Isolate failed login attempts source="/var/log/auth.log" "Failed password"

This surfaced every recorded event where an incorrect password was used to attempt an SSH login — including the source IP and port, which is what an analyst needs to start tracing repeat offenders or brute-force patterns.

Alert configuration

The search was then saved as a scheduled, real-time alert so detection didn't depend on someone manually re-running the query:

  • Title: Failed Login Attempts
  • Alert type: Real-time, expiring after 5 minutes per trigger window
  • Trigger condition: fires per result — every matching "Failed password" event
  • Trigger action: added to Splunk's Triggered Alerts panel
  • Severity: Medium

With the alert saved, any subsequent failed SSH login on the host — attempted with the wrong password — appeared immediately in the Splunk alerts page, giving a live, trackable record of unauthorized access attempts.

Outcome

The finished pipeline demonstrated the full loop a SOC analyst is responsible for: getting the right log source into a SIEM, writing a search that isolates the signal that matters, and turning that search into an alert that surfaces the event without anyone having to go looking for it. It's a small-scale version of exactly the kind of detection logic used in production SOC environments to flag brute-force and credential-stuffing attempts against SSH-exposed servers.
